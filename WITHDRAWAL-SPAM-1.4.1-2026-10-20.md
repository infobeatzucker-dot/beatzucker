# Withdrawal spam protection — prepared 1.4.1

Not deployed. No existing receipts, retention settings, queues or email confirmations deleted or suppressed. No schema migration or external CAPTCHA provider.

Existing email-only rate limits can be bypassed by rotating addresses. New submissions now require a short-lived, HMAC-signed challenge bound to the submission UUID, at least two seconds old and no older than one hour. The DE/EN form prepares this automatically, refreshes expired challenges and preserves the idempotency key on identical retries. A hidden non-focusable honeypot rejects filled bot submissions; rejection never shows a false receipt.

Additional request checks reject explicit cross-site requests. Withdrawal JSON has a separate request budget from login. New requests are limited to 6 per 10 minutes globally, 3 per hour per email and 3 per hour per proxy-verified client where available. A transaction checks stored receipts for a persistent 20/hour global and 3/hour email ceiling before insertion; process restarts do not reset these counts. Existing receipt retries bypass new-submission limits after proof validation. Failure messages retain the email alternative, also always visible below the form. No login, CAPTCHA solving or external tracking required.

Client identity uses only X-Real-IP, never client-controlled X-Forwarded-For. REQUIREMENT: the existing production Next port remains loopback-only and Nginx overwrites X-Real-IP with $remote_addr for /api/withdrawal (the existing general location does). Values are HMAC-hashed with NEXTAUTH_SECRET for temporary limiter keys, never raw-IP database fields. A missing/weak (<32 character) NEXTAUTH_SECRET fails closed with an explicit form/email fallback. Challenge payloads contain only random submission IDs, timestamps and nonce, not personal details. NEXTAUTH_SECRET rotation invalidates old challenges; reload refreshes them.

This reduces unsophisticated automated spam, not a guarantee against adaptive attackers who obtain and wait for fresh challenges. If abuse continues across multiple IPs, consider an external managed bot challenge after consent/privacy/CSP review. Do not delete legal receipts based only on suspected spam. Previously queued spam is not retrospectively removed by this fix and may continue generating queue deliveries.

Validation: dedicated route/crypto tests passed for missing/tampered/early/expired/key-mismatched proofs, honeypot rejection before DB/mail, foreign-site rejection, persistent global/email limits, actual per-client limits across rotating email/XFF addresses, hashed proxy handling and preserved idempotency. All 14 existing audit regressions and 18 account-security tests passed. Production build + TypeScript passed. Actual Chrome DE/EN forms rejected filled honeypots without false receipts and then persisted valid isolated statements with receipt IDs. A blocked challenge request showed reload and email fallback, disabled submission and no false success. QA uses a separate local SQLite database, no production data or external mail. Live deployment remains separate.
